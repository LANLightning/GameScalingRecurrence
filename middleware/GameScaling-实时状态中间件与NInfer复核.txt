GameScaling：NInfer 适配复核与实时状态中间件方案
核对日期：2026-10-25

结论
GameScaling 可以移植到 NInfer。此前失败的是已下载 0.8B-S3 在当前本地引擎上的加载，不是整个模型家族不可转换。已转换的 .ninfer 文件不能证明推理算子支持其尺寸。用户提出的实时状态中间件方向可行，而且不要求模型稳定每秒决策五次；应把策略生成与状态校验/动作撤销分开运行。
本轮新增的是可执行的状态机原型与 19 项合成测试，未连接 Minecraft 实体事件，未读取游戏进程内存，未改变现有模型后端。现有 GameScaling 服务仍是 llama.cpp + 协议适配器。

一、为什么 Bonsai / Qwen3.8-27B 能运行，0.8B GameScaling 加载失败

证据来自本机现用引擎对应源码：
${ENGINE_BASELINE}\build-tools\engine-updates\fusion-20261020\source\src-tree\fusion-engine-src\src\ops\weight_input.cpp
input_projection() 约第 169 行起仅接纳两组指定的 Dense / MoE 投影几何。Dense 隐藏宽度为 5120，MoE 为 2048。GameScaling-0.8B 为 1024。此前真实启动错误为：
text/layers/0: input projection: unsupported logical projection geometry

同源码 docs/maintainer/qwen3_5-model.md 明确说明：配置解析可以接受变化，但算子执行只支持已实现的几何；Qwen3.6-27B 与 Qwen3.8-27B 共用这里的 Dense 几何。
本次重新下载官方 GameScaling-27B-S3/config.json，主要文本配置对比如下：
字段                         GameScaling-0.8B   GameScaling-27B / 引擎 Dense
hidden_size                  1024              5120
num_hidden_layers            24                64
attention heads / KV heads   8 / 2             24 / 4
head_dim                     256               256
GDN key / value heads        16 / 16           16 / 48
GDN key / value head_dim     128 / 128         128 / 128
intermediate_size            3584              17408

因此，你之前转换 Qwen3.8-27B 的经验与目前证据一致。GameScaling-27B 的主要文本几何也匹配，不应被排除。仍需验证视觉模型、权重布局/量化格式、词表特殊 token、聊天模板、GDN 状态和输出语义，不能把几项配置相等说成已加载成功。

两条实现路线：
A. 27B：沿现有 Dense 路径适配权重与协议，先验证数值和输出，再选择量化。普通 27B 的纯 4bit 权重约 13.5 GB（十进制粗算），尚未包含量化元数据、视觉编码器、KV、工作区。不能因 Bonsai 能装下，就推定另一套权重采用相同极低位量化后仍有同等质量或性能。激进量化可以实验，但必须验证游戏策略质量。
B. 0.8B/2B：扩展引擎的投影、GDN 头数组合、视觉尺寸、绑定方式及调度/图捕获支持，检查共享 embedding/output 等差异。不能只删除 require。先逐层对齐参考实现，再做图像、动作和会话回归。
本轮没有实施/完成这两条引擎移植，也没有宣称 NInfer 会比当前后端更快。

KVMem 与 streaming 的术语必须区分：
- 你给的 fork 中 streaming 主要是 KV 页流式调入、逐出和主机驻留管理。
- SSE streaming 是 API 增量输出文本。
- 逐步执行是控制协议允许提前提交局部动作。
三者互相独立。KV 管理不能解决算子尺寸不支持，也不能自动将权重放入不足的显存。其长上下文收益不等于短截图决策低延迟收益；应比较截图到首个可执行动作的 p50/p95、状态撤销时延、显存与策略成功率。
此前对 GameScaling 检查点的张量名称审计未找到原生 MTP 权重。配置出现 mtp_num_hidden_layers 不是可直接启用的证明。跨模型借用草稿头另需匹配与接受率验证，不能沿用 Bonsai 的 MTP 成绩。

二、截图 Base64 与中间生成数据

当前客户端已经使用 Base64：client/gamescaling/policy.py 的 encode_image 生成 data:image/jpeg;base64,...；tools/native_protocol.py 再把图像负载交给后端的 multimodal_data。它没有把 Base64 当普通文本让模型阅读。
Base64 是传输编码，编码长度约为原始二进制的 4/3；它不提供深度、对象状态或更快的视觉理解。JPEG/PNG 压缩、截图采集、视觉编码、prefill、decode 要分别计时。

中间数据有三种完全不同的含义：
1. 游戏中间状态/事件：强烈适合。模型推理期间仍持续处理死亡、目标失效、遮挡、玩家状态和场景切换，必要时立即撤销动作，不等模型输出完。
2. 模型已生成的完整局部意图：可以增量提交，但必须有独立提交边界、完整参数、有限有效期与确定性校验。已执行的前段不能被后文偷偷修改。未完成 JSON、半个坐标、思考片段和未接受的投机 token 均不作为执行依据。
3. Transformer 中间层激活：不是已经结构化的世界状态。若要用作早退决策，需要单独训练/校准读出头或 early-exit 策略，并评估误差与时延。

当前 GameScaling 的训练动作是一整个 200ms chunk：一个全局鼠标位移/滚轮值加六个按键子步。虽然开头较早出现鼠标参数，仍不能把它解释成六个独立的高层计划。可以实验在严格解析完整子步后提前执行，但要定义后段生成停顿、截断、取消、鼠标位移分配和实际动作历史，且要实测收益。默认 runner 目前仍等完整 chunk 后执行。
原型 IntentFrames 仅演示一个新的高层 NDJSON 意图协议可在整段响应结束前交付完整记录；它不是对 GameScaling 原生输出协议的改造或兼容性证明。

三、运行时二进制/内存能不能读取有序数据

可以，通过适配器建立结构和语义。不能成立的是“机器码本身会自动给出有序且正确的实时世界数据”。机器码描述操作，实体字段在数据区/堆中；反编译主要帮助定位方法、字段与生命周期。位置、生命值、可攻击性、场景归属仍需识别并验证。

适合的工作流是：一次性/版本变化时分析 → 找到实体创建、更新、伤害、死亡、回收和复用路径 → 安装轻量观测点或读取结构化状态 → 发布带版本的事件/快照。没有必要每一帧重新反编译。
对于本地 Minecraft Java 版，优先考虑运行中的 Mod 事件/实体 API，必要时 Java Agent、字节码插桩或 JVMTI。JVM TI 提供状态观测与事件接口，但不直接理解 Minecraft 的“可攻击”语义。固定地址方案还要面对堆移动、对象复用、JIT/版本变化与读取撕裂；并非不能做，而是维护与一致性成本更高。
现有目录显示 1.21.1、Java 21 与 NeoForge 相关 Mod，但本轮没有观察实际启动加载器。具体 Hook API 需在该整合包实际运行环境确认后实现。Minecraft 也不能直接使用 Unity C# Editor bridge；可复用的是设计，不是那套接口。

客户端画面、逻辑 tick 和服务器状态应分开标识。更快观察客户端不能提前知道服务器尚未确认的结果。单人世界可从集成服务器取得逻辑状态，并从客户端取得相机/画面；桥接线程不能直接跨线程读取可变实体树，应在对应游戏线程采集一致快照。

推荐状态字段：
instance_id, world_id/dimension, source_epoch, simulation_tick, sequence,
source_timestamp, observed_monotonic_time, authority/provenance,
entity_uuid, spawn_generation, lifecycle, targetable, damageable,
position, velocity, collision/line_of_sight, player/control state。
对象池地址、短期实体编号均不能独立作为身份；使用“世界会话 + UUID/稳定 ID + 生成代数”。对生命周期未识别完整的 Mod 实体，应标 unknown，不猜成 alive。

死亡、不可攻击与 GC 三者独立：
- dead/pooled 对象可以仍有内存；停止攻击不需要等待 GC。
- 暂时不可攻击也可能是无敌、卸载、隐藏或切维度，不能一律记为击杀。
- 只有观察到目标死亡，仍不能证明是本次动作杀死的；击杀归因需要伤害事件、攻击者与因果关联。
- 游戏对象回收由游戏管理。Agent 不需要也不应该把 GC 当作攻击后的业务动作。

四、射线长度与瞄准深度

令眼睛位置 o，归一化视线方向 d，射线 r(t)=o+t*d。
若游戏 raycast 返回首个有效命中点 p，则 t=||p-o|| 是沿该射线的真实几何距离。若方向没有归一化，参数 t 不能直接当米数/方块距离。
maxDistance=100 只是查询上限。无命中不表示目标在 100 的位置，更不能替代测得深度；查询结论还受碰撞层、忽略对象和是否检查流体等条件约束。
一般像素射线的距离与相机前向深度不同：z_camera=(p-o)·camera_forward。中心射线与前向重合时二者相等。
视线方向也不是命中面的表面法线；表面法线描述表面朝向。

攻击验证应使用最近有效遮挡、目标碰撞体、真实攻击范围、玩家冷却和服务器规则。仅方块 raycast 不足以取得怪物距离，要合并实体与方块命中并正确取最近项。眼睛射线与武器/弹丸起点也可能不同。高速移动目标还需速度估计和弹道模型；直线射线本身不解决提前量。
XYZ 目标可由确定性控制器转换为局部方向和 yaw/pitch，让模型决定去哪里/看哪里。若希望 GameScaling 本身直接输出 XYZ/向量，需改变训练/评测或添加适配规划器；换提示词并不能保证得到原有动作水平。

五、复用文档中的五项工程设计


1. 写操作 token + pending：每个意图有 action_id、观察版本、目标生成代数和截止时间；执行后保留待验证状态。发送成功、按键成功、目标状态满足分别记录。取消/过期不是成功，pending 也不意味着事务回滚。
2. verify_assertions：把 alive、targetable、同一实体、可见、范围、状态新鲜、玩家可操作交给确定性代码。在提交前与执行期间反复检查，输出紧凑失败原因。
3. Lua grounding runway：分别管理执行预算和观察/修复预算。你文档记载断言失败也会恢复原预算；游戏版本应要求相关断言通过才恢复执行额度，失败仍允许查询/重规划，不因观察耗尽而陷入无法恢复的状态。它不替代 CPU 时间限额。
4. Recorder/Replay：记录快照/事件、模型输入版本、意图、断言、执行与取消，以及权重、量化、模板、采样设置版本。离线回放默认接假执行器。再次调用真游戏不等于确定性回放；模型也可能非确定性。生产环境用有界事件日志、检查点和丢失检测，不能让日志无限增长。
5. 多实例绑定：绑定游戏进程启动身份、世界/维度、服务会话及实体生成代数；连接恢复后重新握手，旧会话命令失效。窗口标题或 PID 单独不够。

六、推荐闭环：模型慢决策，状态驱动快速撤销

游戏线程事件/快照 → 状态中间件 → 确定性执行守卫 → 游戏线程动作
                            ↑                    ↓
                      模型策略/短期计划 ← 断言结果/实际动作回执

模型回答“接下来尝试什么”；中间件始终回答“这个动作此刻还成立吗”。
每个动作定义三类条件：
- 前置条件：同一世界、目标代数、可攻击、范围、视线和数据新鲜。
- 过程不变量：玩家可操作、目标仍符合条件、动作租约未到期。
- 后置证据：目标已失去攻击资格/玩家到达容差范围等；业务目标与因果归因单独判断。

不要在每个世界版本变化时取消全部计划，否则任何无关实体变化都导致重算。维护动作依赖集，相关条件变化才撤销；允许旧规划在最新状态重新验证后继续。
也不要把“确保方向正确”说成绝对保证：断言只能约束已采集、已建模的事实。还需要进展指标，例如一段时间内距离没有减少、反复碰撞或攻击无有效回执时触发重规划；保持有效但毫无进展同样是失败。

关键并发边界：外部进程读取状态后再 SendInput，检查和执行间仍有竞态。最强的方案是 Mod/游戏线程在执行点重新检查目标与条件，然后提交动作。外围中间件提前取消能缩小风险，但无法撤销游戏已经消费的输入。原型假定事件采集和执行守卫在同一串行逻辑上运行；并未证明 Win32 输入注入能实现原子控制。
实际总撤销延迟 = 游戏状态发布延迟 + 传输/排队延迟 + 守卫调度延迟 + 游戏消费释放动作的延迟，不再必须加上完整模型推理等待，但也不是零延迟。
事件通道需要有界队列与背压。位置更新可合并，死亡、代数变化和断连等关键事件不能静默丢弃；发现 sequence 缺口，暂停相关动作并请求新完整快照。定期快照修复漂移。
历史上下文必须写入实际执行轨迹/取消回执；如果只执行了部分 200ms chunk，不能把完整计划作为“已经发生”的历史。原 runner 目前没有这种实体语义回执，接入时必须一起修改。

七、借鉴识图性能优化，但不夸大收益

文档历史测量的 313.92→52.07ms 优化是默认观察不再截图，不是视觉编码/截图本身快六倍；full 截图历史为 311.54→318.11ms。这些不是本轮重测。
可迁移的设计：
- 高频状态/断言路径只传结构化变化，不每次截图、JPEG、Base64和视觉推理。
- 当语义任务改变、需要辨认未知目标、结构化状态与视觉证据冲突，或视觉证据到期时再采图。
- 保留定期视觉校验，避免状态适配器遗漏 UI、遮挡或 Mod 语义。
- 图像 file_ref/shared memory 可减少复制和大字符串传输，但接收端必须真实支持它；当前接口只接受 Base64，不应直接改传路径字符串。
- 缓存带 frame_id/tick、相机姿态、分辨率与变换信息。裁剪/缩放改变瞄准坐标，需恢复到原图；多尺度/局部裁剪是否保持策略质量要单独测。
- 不同帧不能简单复用旧视觉 embedding；相机变化和动作历史会改变任务语义。

GameScaling 原本是视觉动作策略。减少守卫循环的截图，不意味着将模型实际调用时所需的图像全部删除；纯状态规划可以由独立控制器/规划模型承担，或训练支持状态输入的新策略。
CPU vision 可以省显存，但是否更快取决于 CPU、GPU 并发与数据搬运。KVMem 能管理上下文，也不能替代传感器采样。建议拆分采集、编码、IPC、视觉编码、prefill、首个完整意图、断言、执行和撤销的 p50/p95，固定场景与热身条件比较。

八、本轮可执行原型及验收边界

state_guard.py：绑定世界、实体生成代数、带时限攻击意图、pending、断言、执行预算、有界记录；支持状态到达时撤销与 tick 超时撤销。
test_state_guard.py：19 个合成行为场景。
state-guard-test-results.json：结果清单。
state-guard-example.jsonl：已接受攻击随后目标死亡、释放攻击的事件记录。

复现命令（在这些文件所在目录运行）：
${LOCAL_PATH} test_state_guard.py

已通过：模型生成期间死亡后拒绝旧动作、执行中死亡撤销、池内残留、仅不可攻击标志、同 ID 复用、乱序旧包、序列缺口、源重启、断流、动作到期、错误实例、无关变化、遮挡/距离/NaN、非权威源、重复动作、失败断言不恢复预算、消失不等于击杀、完整中间记录先交付、玩家死亡/菜单中断。
测试仅验证合成状态机；运行耗时不代表 Minecraft 端到端延迟。原型不含生产传输鉴权、线程接入、持久化回放服务、完整移动/弹道/冷却控制器、模型意图到真实实体的绑定、活体 Minecraft 传感器及实际动作执行器。内存是否存在只是模拟状态，不是进程采样结果。

建议下一阶段以此整合包的真实加载器为准，做一个最小实体观察桥：玩家姿态、附近实体生命周期、目标 raycast、游戏 tick 与世界会话。先只读记录并对照画面，确认池化/死亡语义，再把同线程执行断言接进去。这样可以逐步验证获取到的是“游戏语义”，而不只是一些看似合理的内存数值。
