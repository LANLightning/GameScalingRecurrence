# 两套模型的精度与文件布局差异

本次比较的是同一 GameScaling-0.8B-S3 检查点的两种部署：**NInfer + BF16/CUDA** 与 **llama.cpp + Q8_0/Vulkan**。它们不是两种不同训练出来的智能体，也不能把结果当成纯 NInfer 对纯 llama.cpp 的等精度测速。

## BF16 和 Q8_0 是什么

| 项目 | BF16 | Q8_0 |
|---|---|---|
| 权重表示 | 16 位浮点：1 位符号、8 位指数、7 位尾数 | 分块量化；每 32 个权重存 32 个有符号 8 位整数和一个 16 位缩放值 |
| 单个被转换权重的理论存储 | 2 字节 | 平均 34/32 = 1.0625 字节，即 8.5 bit/权重 |
| 数值变化 | 有浮点舍入误差，动态范围接近 FP32；并非 FP32 原样保留 | 权重近似为缩放值乘整数；会有量化误差，较小值可能被舍入到零 |
| 典型影响 | 权重带宽和存储开销较大 | 通常减少权重存储和搬运量，但要做量化相关运算；不保证总延迟一定更低 |

Q8_0 的 8 位指权重存储形式，不代表所有激活、乘加、累加器和 KV Cache 都是 8 位。本次 BF16 也不表示整个推理过程的所有中间值都只用 BF16。BF16 与 FP16 都占 16 位，但指数/尾数分配不同；视觉 F16 文件不能称为 BF16。

量化不会新增 UI 树、规划器、创造能力或训练知识。它可能通过改变 logits 影响某次按键/转向选择；温度 1 的采样、不同内核和后续不同画面又会继续放大轨迹差异。因此不能把两端这次行动差异全归因于 Q8，也不能承诺 BF16 一定能完成 Q8 没完成的目标。

## 对本机实际文件的检查

以下来自直接读取已部署文件的张量目录，而非根据文件名猜测。完整机器可读记录见 [model-precision-audit.json](../evidence/model-precision-audit.json)。

| 文件 | 实际权重类型 | 文件大小（十进制字节） |
|---|---|---:|
| gamescaling-0.8b-s3-bf16.ninfer | 365 个 BF16 张量对象，36 个 FP32 张量对象；合并文本和视觉 | 1,717,196,800 |
| GameScaling-0.8B-S3-Q8_0.gguf | 188 个 Q8_0 张量，133 个 FP32 张量 | 1,082,015,776 |
| mmproj-GameScaling-0.8B-S3-F16.gguf | 52 个 FP16 张量，102 个 FP32 张量；视觉编码/投影部分 | 204,987,200 |

因此本次 llama.cpp 组合是 **Q8_0 + FP16 + FP32 混合存储**；NInfer 是 **BF16 + FP32 混合存储**。llama.cpp 两个模型文件合计 1,287,002,976 字节，相对 NInfer 文件少约 **25.1%**，并非一半。文件大小不等于实测显存：还需加入 KV、工作区、CUDA/Vulkan 图和游戏占用。

为什么不是一半？除了缩放信息、元数据、不同精度的视觉部分，本次文件的共享权重布局也不同：

- 原配置 tie_word_embeddings=true。
- NInfer 的 text/token_embedding 与 text/output_head 都绑定到同一对象 weight/000090。
- 当前 GGUF 同时存放 token_embd.weight 和 output.weight，各占 270,172,160 字节；两者 SHA-256 完全相同。这是同一份共享权重在文件中存了两份，不能据此说 GGUF 模型多训练了参数。

核对总数也一致：NInfer 独立权重元素为 852,985,920；GGUF 两文件存储 1,107,265,600 个元素，扣除重复输出头的 254,279,680 个元素后，也为 852,985,920。

这些是当前转换产物的事实，不是“所有 GGUF 必然复制权重”或“所有 NInfer 必然更省内存”的结论。

## 本次速度结论应如何表述

五分钟实机记录里，平均截图至响应时间为 NInfer 1075.05 ms、llama.cpp 969.08 ms，后者约少 106 ms。准确表述是：**当前两套部署在各自这轮游戏轨迹中的端到端耗时不同**。

同时变化的因素包括：BF16/Q8 权重、BF16/FP16 视觉权重、CUDA/Vulkan、专用算子与执行图、KV 策略、上下文容量（启动上限分别为 32768/16384）、输出 token 数，以及 Minecraft 画面和运行负载。五分钟测试不是固定输入的等精度引擎基准。它们均未完成完整目标。

若要进一步分开“量化收益”和“引擎收益”，应先在同一 llama.cpp 后端比较 BF16 与 Q8 的固定截图/固定历史请求，再用尽量一致的 BF16 文本、视觉精度、模板、KV 设置与输入比较两引擎；分别报告首 token、首可解析动作、完整响应和动作实际生效时间。不同引擎同种子也不保证相同 token。**这些等精度对照尚未实施，本次不把它们写成已完成。**
