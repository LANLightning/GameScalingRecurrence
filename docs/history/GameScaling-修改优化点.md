## 你的工程优化思路：落地状态

| 思路 | 可复现的设计结论 | 当前状态 |
|---|---|---|
| 中间件记录实时世界变化 | 游戏 tick/事件产生带序号、时间、实体 generation 的状态；模型建议绑定快照版本，执行前检查最新状态 | `middleware/state_guard.py` 原型，19 项合成测试；未接 Minecraft |
| pending-token 写操作约束 | 模型先提出意图，执行器凭短期租约与状态断言放行 | 原型；不是游戏写操作已接管 |
| `verify_assertions` | 确定性代码检查 alive/targetable、射线可达、距离、状态新鲜度；失败停止/重规划 | 原型 |
| grounding runway | 限制连续未验证动作预算；只有断言通过才重置预算 | 原型 |
| Recorder / Replay | JSONL 记录输入、动作、断言与结果；重放不等于确定性复现整个游戏 | 已有记录原型；实机测试另保存图片/原始动作 |
| 多实例绑定 | 最终绑定实例 ID/进程/世界/会话 epoch；只靠窗口标题不足 | 当前仍靠前台 Minecraft 标题，强绑定待做 |
| 幽灵实体与对象缓存 | “死亡/不可攻击”是游戏语义，不能用是否 GC 回收判断；ID 复用需 generation | 原型表达了这些状态，尚无实际游戏数据源 |
| 逐层/中间决策 | 只提交完整、可解析、经状态验证的动作分段；隐藏层张量不能直接当可信指令 | 已测首段出现时间；执行器仍等完整动作 |

推荐后续控制链：`游戏事件/快照 → 状态中间件 → 模型建议 → 最新状态断言 → 短动作执行 → 游戏回执 → 必要时重规划`。模型慢不意味着状态监视也必须慢。

## 图像、坐标与 UI 的结论

- **Base64**：已用于传图，只是编码；不会增加深度信息或免除视觉计算。RGB 图像本来就是像素矩阵，不需要重新发明“颜色矩阵识图”。
- **XYZ 与 aim 向量**：模型当前输出仍是鼠标增量与按键。可增加世界坐标控制器把目标点/方向转换为输入，但需要游戏位姿、相机参数与碰撞信息；修改提示词不能改变训练好的动作接口。
- **射线深度**：方向向量不包含距离；射线与真实碰撞体/深度缓冲的首个有效交点能给出命中距离。人为给定射线长度只定义检测范围。
- **运行时内存/机器码**：不是现成的有序世界状态。Java 对象布局、JIT、GC、缓存实体、客户端与服务端状态都需适配；本例优先用 NeoForge Mod/受控 Java 桥读取逻辑状态，而非硬编码内存地址。
- **通用 UI 树**：统一语义结构（角色、文本、矩形、父子关系、可操作性、来源、置信度），底层按 UI 引擎接适配器。自绘/ImGui 可能没有可直接读取的持久树；像素只能推断近似语义树。未实现。
- **“建村民小屋”**：可传自然语言目标，现有 `--goal` 已支持；可靠建造仍需规划、材料/配方/空间状态及执行验证。0.8B 当前连“向左看”也未稳定遵循，不能宣称已有可靠创造性能力。
- **预览**：适合先生成平面/线框图、方块清单与差异预览，再经明确执行流程落地。无需以修改机器码作为建造前提；未实现。

## 性能优化的边界与下一步

1. 先修通真实键鼠输入并验证可观察位姿变化；Windows 返回成功不等于游戏收到动作。
2. 用真实 Minecraft 连续画面评测“不操作率、目标完成率、过期动作拒绝率”，不能只看格式正确和 tok/s。
3. 状态桥优先返回紧凑状态/差量，按需截图。用户 UnityMCP 文档中的 314→52 ms 是“默认观察不再截图”的工作量变化，不是视觉模型整体快 6 倍。
4. NInfer 可继续优化小批量 decode 专用核并验证 Q8；当前复用 prompt 注意力内核，仍有性能空间。没有 MTP 权重时，不能靠配置项创造 MTP。
5. 保留 BF16/FP64 参考、缓存写回与状态一致性测试。量化、加大动作块、减少画面 token 都须同时检查游戏质量。

当前证据：32 次真实游戏图像请求可解析；温度 0 全部不操作，温度 1 有部分动作但目标方向不稳定；键鼠校准未通过。**部署可复现，不等于自动玩游戏已验收。**
