## 可复核条件

- 硬件：RTX 4070 Laptop，8188 MiB 显存。两后端与 Minecraft 同时驻留，交替顺序、顺序请求；每组正式样本中各有 12 次先请求、12 次后请求。GPU 温度从 55°C 到 69°C。
- 模型：同一 GameScaling-0.8B-S3 检查点，NInfer 为 BF16 + FP32/CUDA，llama.cpp 为 Q8_0/Vulkan + F16 视觉投影。量化和实现不同，结果描述本机部署，不代表严格同精度的引擎比较。
- 每组先预热 3 对，再测 24 对。温度 0 组先测，温度 1 组后测；两组之间有温度/运行时段混杂，不能将组间耗时差全归因于采样温度。
- 同对共享同一 JPEG/Base64 字符串，记录 SHA256；48 张正式图像哈希不同。截图均为 854×480，JPEG quality=90，max_tokens=2048，history_len=0，reasoning=False。
- 缓存实测：两端输入均为 1303 token；NInfer 每次报告 cached_tokens=0，llama.cpp 每次报告 cached_tokens=787。当前部署缓存复用不对称，这是解释速度差的重要条件。NInfer 已启用 KVMem，并不意味着变化截图请求就自动复用前缀；这里不能推断其所有内部缓存均未命中，也不能从此测量分离缓存收益和算子速度。下一项性能工作应验证变化图像下的安全前缀复用，再做控制变量测试。
- P95 使用 nearest-rank。记录所有原始文本、token 数、缓存数、顺序、耗时和 PNG。没有清空服务器缓存，因此描述热服务；逐请求缓存信息见 JSONL。
- 温度 0 两端全部输出相同的 29-token 不操作动作；温度 1 两端 token 数中位数均为 30，但分布不同（NInfer 29–42，llama.cpp 29–40）。本轮均以 stop 正常结束，没有长度截断。
- 首末截图显示夜间山谷，玩家视角基本固定；相邻帧像素平均差约 0.029/255。存在天空等变化，但这不是移动、战斗或多场景覆盖。
- 温度 1 两端各有 22/24 次非零动作输出，但没有执行，不能判定其方向正确或任务完成。不得将输出非零等同于可玩性。
- 之前 SendInput 校准虽返回成功，用户与截图均未确认游戏移动。输入故障仍未定位，本次没有把它改写为通过；也没有 vLLM 实测。

## 官方流程与本次对应关系

官方链路是：当前截图与近期已执行动作 → 专用聊天模板、assistant prefill → 模型 → 解析约 200 ms 的六段键鼠动作 → 游戏执行器 → 下一帧。服务示例使用 vLLM，默认历史为 5。见 [官方说明](https://huggingface.co/THUSI-Lab/GameScaling#6-running-it-in-a-game)。

本次保留原模板、动作格式和前缀，测无思考模式；历史设 0，因为没有实际执行动作，不能把模型建议伪装成已执行历史。使用 NInfer/llama.cpp 兼容接口替代 vLLM。官方支持把 Action 交给自定义执行器，文档没有替我们解决 Minecraft 输入问题。默认 200 ms 描述动作块覆盖时长，不是保证 200 ms 内完成一次推理。

## 新机器最短复测

先按同目录 `GameScaling-快速复现.md` 完成部署并启动两个后端，将 `benchmark_live_paired.py` 放到部署根目录。进入测试世界后运行：

```bat
runtime-env\Scripts\python.exe benchmark_live_paired.py --root . --out reports\live-speed-new --pairs-per-temperature 24
```

60 秒内切回 Minecraft，保持前台约 1 分钟；这是只观察的测试，不操作角色。已有同名 records.jsonl 时会拒绝覆盖，请使用新输出目录。检查 summary.json 的 stop_reason=completed、每组 n=24、valid=24；records.jsonl 保留逐请求证据。窗口标题只做弱绑定，请关闭其他 Minecraft 窗口。

证据包 `Minecraft-实时配对测速-20261026.zip` 包含本轮 54 张截图（含预热）、108 条请求、提示词、元数据、统计、脚本与源码哈希；不含模型权重。
